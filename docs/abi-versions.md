# Driver versions

`crates/nvrm-sys` carries a measured struct layout for every NVIDIA driver
version this project supports, and the compiler checks every offset in it.
Everything under that crate except `src/version.rs` is generated by
`cargo xtask abi` from exactly two hand-maintained inputs:

  * **`crates/nvrm-sys/abi.toml`** — which versions, what is bound, which
    types the boundary reads, and which of NVIDIA's renames are renames.
  * **`vendor/nvidia-rm-headers/<version>/`** — the headers themselves,
    copied verbatim from the upstream tag, with the commit and the licence in
    `PROVENANCE` beside them. Never edited.

`crates/nvrm-sys/manifests/<version>.json` is the evidence: the size, the
alignment and every field offset of every bound type, per version, committed.
A claim that two versions have the same footprint is checkable with a diff, by
a reader with no card and no driver.

## Adding a version

    ./scripts/build.sh vendor-abi <version>     # the headers, ~25 KB packed
    # add one [versions."<version>"] entry to crates/nvrm-sys/abi.toml
    cargo xtask abi

Three things can happen, and only the third needs a person.

**Identical.** The new version's manifest matches one already there. Nothing
else to do: the entry makes it buildable, and `cargo xtask abi` puts its names
in `src/stable.rs` with the rest.

**Append-only.** A struct grew at the end, every old offset unchanged, and
nothing contains it by value. The generator handles it without being asked —
the new version gets its own module and its own `RmAbi` impl, and an older
caller reads the same bytes it always did.

**Breaking.** A struct the boundary reads changed shape. The generator
**stops**, names the struct, says what moved, and prints the lines to paste:

    [versions."610.57.04".layout]
    NV_CHANNEL_ALLOC_PARAMS = "v610"

That entry does not describe the layout — the layout is still measured. It
records that somebody looked. An entry that stops applying is an error too;
stale prose about a move that is no longer there is worse than none.

Only **mediated** structs stop the generator (`[footprint.mediated]`). There
are 93 to 168 breaking types between any two versions and almost all of them
are internal controls nothing here intercepts; a question nobody can answer
usefully is not a safeguard.

## What is supported

The two current datacenter LTSB branches and the two newest production or
feature branches, **each at its latest minor release**. One entry per branch.

An older minor of a supported branch is supported only if its manifest
**matches** the entry — it is then the same bytes and needs no entry of its
own. If it does not match, it is refused. `DriverVersion::from_version_string`
returns `None` for a version with no entry, and the backend stops rather than
reaching for the nearest layout.

**A branch is not a layout.** Measured 2026-09-14 over twelve upstream tags:
580.167.08, 580.173.02 and 580.178.04 are identical to each other, and so are
595.91.07 and 595.99.02 — but inside R610, 610.43.02 and 610.43.03 are
identical to each other and *not* to 610.57.04, which appended eight bytes to
one struct. R610 carries two layouts and only the later one is here. See
`OPEN-QUESTIONS.md` number 72.

When a branch reaches end of life its entry and its layout module go; its
manifest stays in `manifests/` as history and `cargo xtask abi` says so on
every run rather than letting the directory read as uniformly current.

## What "supported" does not mean

It means the offsets are right and the compiler checks them. It does not mean
the boundary works on that driver: a layout can be correct while a control
this tree has never sent is refused. That is a separate, measured claim, and
it is the table below.

Measured before this script existed, and stated here rather than folded into
the table below, because they were not produced by it:

  * **610.57.04 on Turing, RTX 2070 (compute 7.5).** `ioctl-matrix.sh` against
    a native baseline on 2026-08-21: **290 signatures** catalogued,
    `matrix/catalog-610.57.04.json`, with `matrix/guest-610.57.04.json`
    recording 9 guest-validated probes, 2 blocked and 10 FAIL. This is the
    pair every measurement in this tree rests on.
  * **610.57.04 on Blackwell consumer, RTX 5060 Ti (compute 12.0).** The gates
    passed — `gpu` 8/8, `vdisplay` 6/6 — and the descriptor table checksum
    (`0xad009afd`) and the virtual display's frame hash
    (`0xb6a79817d7f4a5c3`) were identical to Turing's. `ioctl-matrix.sh` has
    **not** been run on that card, so it is deliberately not a row: a gate is
    a verdict and the matrix is a differential, and `OPEN-QUESTIONS.md`
    number 56 is about why the difference matters.

Each row below is one run of `scripts/abi-verify.sh` on a host with that
driver and that card. The table is generated from `matrix/abi-verify-*.json`,
so it cannot name a pair nobody ran.

## Measuring a pair

    # install the driver on the host, then:
    export LEA_DRIVER=<version>
    ./scripts/build.sh vendor        # the catalogue resolves against these headers
    ./scripts/abi-verify.sh          # check band, gpu gate, the ioctl matrix
    ./scripts/abi-verify.sh table    # fill the table above

`LEA_DRIVER` points one run at a driver other than the one in
`DRIVER_VERSION`, which stays what the tree is BUILT for. Three things make
that enough, and all three are properties rather than conveniences:

  * the backend reads the running driver once, in `nvrm::serve`, and picks the
    layout there — every caller below it is generic over `A: RmAbi` and never
    asks again;
  * the guest's NVIDIA userspace is copied from the host at rig-up, so it
    follows the host driver without an image being rebaked;
  * the guest module reads the descriptor table off the wire instead of
    carrying sizes, and the host builds that table for the running version.

**The guest module does not have to be rebuilt between 595, 610 and 615.**
Measured 2026-09-14: the header `nvrm-genhdr` generates is byte-identical for
those three. 580.178.04 differs, by exactly the seven `NVRM_CTRL_VD_*` and
`NVRM_CLASS_DISPLAYLESS` defines — that driver has no `NVA083_GRID_DISPLAYLESS`
class at all, so a 580 module has no virtual display. What that means for the
display path is `OPEN-QUESTIONS.md` number 74.

The descriptor table itself moves more than the header does:

| driver | table stream | checksum |
|---|---|---|
| 580.178.04 | 6968 bytes | `0xef9642f5` |
| 595.99.02 | 6968 bytes | `0xef9642f5` |
| 610.57.04 | 6968 bytes | `0xad009afd` |
| 615.71.09 | 6968 bytes | `0x595934d5` |

Same size on all four, three distinct contents: 580 and 595 agree,
610 differs by `NV_CHANNEL_ALLOC_PARAMS` (368 to 376 bytes) and 615 by the TSG
params (20 to 28). Regenerate any of them with
`cargo run --all-features --bin nvrm-genhdr -- --abi <version> --dump-tables <file>`.

## What the check band checks

`scripts/test.sh check`, step `abi`: `cargo xtask abi --check` must produce no
diff, and `nvrm-sys` must build with each version's feature alone and with all
of them at once. Features are additive by construction — each `v<NNN>` enables
a module and disables nothing, and there is deliberately no "exactly one
version" feature, because cargo unifies features across a build and such a
thing would turn one crate's choice into everyone's.
